Webhooks ​

Concept ​

SIMAST notifies your application when a data request finishes processing, and when the results of a person search change, by sending a POST request to the callback_url configured on your Application (set during application registration via the Partner portal).

This is a simple, one-way, fire-and-forget notification — it only signals that something happened. It carries no request data itself and does not trigger anything else automatically.

Independent from the retro pull: notifications and the retro pull are two separate mechanisms sharing the same callback_url and webhook_secret, but signed differently (see below) and triggered independently. Receiving a webhook does not mean a retro pull will follow, and the retro pull is not gated by webhook delivery succeeding.

Events ​

Four possible terminal events, depending on how the request's parts (including any extensions) resolved:

EventSent when
demande.completedEvery part completed successfully.
demande.partially_completedAt least one part completed, and at least one other part failed or was rejected.
demande.failedAt least one part failed, and none completed.
demande.rejectedThe request itself was rejected before processing — no extension or further action is possible on it afterward.

All four share the same envelope and payload shape:

POST {callback_url}
X-Webhook-Signature: {signature}
X-Webhook-Timestamp: {unix_timestamp}
X-Webhook-Event: {event}
X-Webhook-ID: {uuid}

{
  "event": "demande.partially_completed",
  "event_id": "uuid",
  "company_id": "uuid",
  "application_id": "uuid",
  "data": {
    "id": "uuid",
    "status": "PARTIALLY_COMPLETED",
    "summary": {
      "total": 3,
      "completed": 2,
      "failed": 1,
      "rejected": 0
    },
    "details": [
      { "id": "uuid", "type": "DATA_LIST", "status": "COMPLETED" },
      { "id": "uuid", "parent_id": "uuid", "type": "DATA_LIST", "status": "FAILED" }
    ]
  },
  "timestamp": "2026-04-10T12:00:00Z"
}
  • event_id — same value as the X-Webhook-ID header; safe to use for deduplication.
  • data.id — the request's uuid.
  • data.status — mirrors event (COMPLETED / PARTIALLY_COMPLETED / FAILED / REJECTED).
  • data.summary — counts across every part of the request, extensions included.
  • data.details — one entry per part. parent_id is present only on extensions and points to the part it extends.
  • data.details[].include — present only on an inclusion sub-request: { "requested": 2, "eligible": ["…"], "not_eligible": ["…"] }.

For a failed or rejected part, retrieve the reason via the request detail endpoint if needed for troubleshooting — useful if the webhook delivery itself is missed.

search.updated ​

Sent for a person search, with the same envelope and headers as above:

  • when the automatic processing of a search or sub-search ends, or fails;
  • at the end of each review session of a SIMAST analyst.

One notification per processing or session, never one per person.

json
{
  "event": "search.updated",
  "event_id": "uuid",
  "company_id": "uuid",
  "application_id": "uuid",
  "data": {
    "id": "uuid",
    "status": "COMPLETED",
    "search": { "id": "uuid", "status": "COMPLETED" },
    "summary": { "total": 11, "match": 8, "revision": 2, "no_match": 1 },
    "items": [
      { "id": "uuid", "external_ref": "PL-001", "status": "MATCH", "menage_code": "0001-00001", "membre_rang": 1, "menage_version": 2025, "reason": null },
      { "id": "uuid", "external_ref": "PL-003", "status": "NO_MATCH", "menage_code": null, "membre_rang": null, "menage_version": null, "reason": "DONNEES_INSUFFISANTES" }
    ]
  },
  "timestamp": "2026-09-30T12:00:00Z"
}
  • data.id and data.status — the root search, even when the notification concerns a sub-search.
  • data.search — the search (root or sub-search) whose automatic processing ended, with its status. FAILED means the processing failed: its persons stay in REVISION and are handled by SIMAST. null for the end of an analyst review session.
  • data.summary — counts over the root search and all its sub-searches.
  • data.items — only the persons whose status changed in this processing or session. status is MATCH, REVISION or NO_MATCH; reason is set for NO_MATCH only (see reasons).
  • On MATCH, menage_code, membre_rang and menage_version identify the household and the member: fetch the household from Search Data.

Verifying the Signature ​

X-Webhook-Signature is computed over {timestamp}.{raw_body} (the exact value of X-Webhook-Timestamp, a dot, then the raw request body) using HMAC-SHA256 with the webhook_secret configured on the application — the same secret used for the return URL signature, but the payload signed is different: here it's {timestamp}.{raw_body}, there it's {applicationUuid}|{demandeDetailUuid}.

js
function isValidSimastWebhook(rawBody, timestamp, receivedSignature, webhookSecret) {
  const expected = crypto
    .createHmac('sha256', webhookSecret)
    .update(`${timestamp}.${rawBody}`)
    .digest('hex');
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(receivedSignature));
}
php
function isValidSimastWebhook(
    string $rawBody,
    string $timestamp,
    string $receivedSignature,
    string $webhookSecret
): bool {
    $payload = "{$timestamp}.{$rawBody}";
    $expected = hash_hmac('sha256', $payload, $webhookSecret);
    return hash_equals($expected, $receivedSignature);
}
python
import hmac
import hashlib

def is_valid_simast_webhook(raw_body, timestamp, received_signature, webhook_secret):

java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.security.MessageDigest;
import java.nio.charset.StandardCharsets;

public boolean isValidSimastWebhook(String rawBody, String timestamp,
                                     String receivedSignature, String webhookSecret) throws Exception {
    String payload = timestamp + "." + rawBody;
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(webhookSecret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
    byte[] hash = mac.doFinal(payload.getBytes(StandardCharsets.UTF_8));
    StringBuilder hex = new StringBuilder();
    for (byte b : hash) hex.append(String.format("%02x", b));
    String expected = hex.toString();
    return MessageDigest.isEqual(
        expected.getBytes(StandardCharsets.UTF_8),
        receivedSignature.getBytes(StandardCharsets.UTF_8)
    );
}
csharp
using System;
using System.Security.Cryptography;
using System.Text;

public bool IsValidSimastWebhook(string rawBody, string timestamp, string receivedSignature, string webhookSecret)
{
    var payload = $"{timestamp}.{rawBody}";
    using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(webhookSecret));
    var hash = hmac.ComputeHash(Encoding.UTF8.GetBytes(payload));
    var expected = Convert.ToHexString(hash).ToLowerInvariant();
    return CryptographicOperations.FixedTimeEquals(
        Encoding.UTF8.GetBytes(expected),
        Encoding.UTF8.GetBytes(receivedSignature)
    );
}
go
import (
    "crypto/hmac"
    "crypto/sha256"
    "encoding/hex"
    "fmt"
)

func isValidSimastWebhook(rawBody, timestamp, receivedSignature, webhookSecret string) bool {
    payload := fmt.Sprintf("%s.%s", timestamp, rawBody)
    mac := hmac.New(sha256.New, []byte(webhookSecret))
    mac.Write([]byte(payload))
    expected := hex.EncodeToString(mac.Sum(nil))
    return hmac.Equal([]byte(expected), []byte(receivedSignature))
}
ruby
require 'openssl'

def valid_simast_webhook?(raw_body, timestamp, received_signature, webhook_secret)
  payload = "#{timestamp}.#{raw_body}"
  expected = OpenSSL::HMAC.hexdigest('SHA256', webhook_secret, payload)
  OpenSSL.fixed_length_secure_compare(expected, received_signature)
end
  • Reject the request if timestamp is more than ~5 minutes old (anti-replay window).
  • X-Webhook-ID is a delivery identifier — safe to use for deduplication if a delivery is retried.
  • Secret rotation: when a partner regenerates their webhook_secret from the Partner portal, the previous secret stays valid for 24h. During that window, if verification with the current secret fails, retry with the previous secret (communicated once, at regeneration time, by the Partner portal) before rejecting the request.

Security Note ​

X-Webhook-Signature guarantees the notification's authenticity (it came from SIMAST) and integrity (the payload wasn't altered in transit) — provided you actually verify it, in constant time, and check the timestamp freshness above. It does not by itself guarantee confidentiality: use an HTTPS callback_url so the payload isn't readable in transit (required by SIMAST for PRODUCTION/STAGING applications).

Related: Return URL — the separate, mandatory mechanism SIMAST uses to retrieve data back from your application; a partner cannot opt out of implementing it and still receive SIMAST household data.
