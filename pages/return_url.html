Return URL ​

Concept ​

The base URL SIMAST calls to retrieve updated data after a request has been processed is the callback_url configured on the Application (set once, during application registration via the Partner portal). There is no per-request field for this — every retro pull for a given Application lands on the same callback_url.

SIMAST constructs the actual call URL by appending the DemandeDetail UUID and an HMAC-SHA256 signature to callback_url. The request also carries the signature and timestamp as headers — same convention as the webhook POST:

GET {callback_url}/{demandeDetail_uuid}/{hmac_signature}
X-Webhook-Timestamp: {timestamp}
X-Webhook-Signature: {hmac_signature}

The signature is sent twice, in the same request — once as the last path segment and once as the X-Webhook-Signature header. Both carry the exact same value.

Migration path: the URL shape shown above — signature in the trailing path segment — is what SIMAST sends today for backward compatibility with existing integrations. The X-Webhook-Signature header is the recommended way to read the signature going forward. Over time, SIMAST will migrate to sending only the recommended format — GET {callback_url}/{demandeDetail_uuid} with the signature exclusively in the header, no trailing signature segment. No removal date is set yet; integrations still reading the path segment should plan to migrate to the header to avoid a future break.

This means the third-party application must expose a GET endpoint that accepts two path segments after callback_url — the same base URL already used to receive the POSTwebhook notifications (demande.completed/demande.failed/etc.). In practice, your callback_url handler needs to route on HTTP method: POST for webhook events, GET /{demandeDetail_uuid}/{hmac_signature} for the retro pull.

This is mandatory, not optional. Implementing this GET endpoint is a requirement to receive SIMAST household data — there is no alternative delivery mechanism a partner can use instead. Every Application must have a callback_url configured (required at registration).

Extended requests: when a request is extended to fetch additional households, the extension is not a separate request for retro-pull purposes. The demandeDetail_uuid used in the return URL stays the one from the original request — extending it never produces a new UUID to track or a new signed URL to expose. One callback_url handler, one demandeDetail_uuid, regardless of how many times a request has been extended.

Security — Signature Verification ​

The URL called by SIMAST is signed using HMAC-SHA256 with the webhook_secret configured on the application (set during application registration via the Partner portal).

The third-party application must verify this signature before returning any data. This ensures that only SIMAST can trigger the retro pull.

The signed payload is {timestamp}.{applicationUuid}|{demandeDetailUuid} — the exact value of the X-Webhook-Timestamp header, a dot, then the application UUID and the DemandeDetail UUID joined by |. The examples below read receivedSignature from the X-Webhook-Signature header (recommended); if your integration still reads it from the last URL path segment instead (legacy), the rest of the verification logic is identical — it's the same value either way.

Verification logic:

js
const crypto = require('crypto');

function isValidSimastRequest(applicationUuid, demandeDetailUuid, timestamp, receivedSignature, webhookSecret) {
  const expected = crypto
    .createHmac('sha256', webhookSecret)
    .update(`${timestamp}.${applicationUuid}|${demandeDetailUuid}`)
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(receivedSignature)
  );
}
php
function isValidSimastRequest(

java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.security.MessageDigest;
import java.nio.charset.StandardCharsets;

public boolean isValidSimastRequest(String applicationUuid, String demandeDetailUuid,
                                     String timestamp, String receivedSignature,
                                     String webhookSecret) throws Exception {
    String payload = timestamp + "." + applicationUuid + "|" + demandeDetailUuid;
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(webhookSecret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
    byte[] hash = mac.doFinal(payload.getBytes(StandardCharsets.UTF_8));
    StringBuilder hex = new StringBuilder();
    for (byte b : hash) hex.append(String.format("%02x", b));
    String expected = hex.toString();
    return MessageDigest.isEqual(
        expected.getBytes(StandardCharsets.UTF_8),
        receivedSignature.getBytes(StandardCharsets.UTF_8)
    );
}
csharp
using System;
using System.Security.Cryptography;
using System.Text;

public bool IsValidSimastRequest(string applicationUuid, string demandeDetailUuid,
                                  string timestamp, string receivedSignature, string webhookSecret)
{
    var payload = $"{timestamp}.{applicationUuid}|{demandeDetailUuid}";
    using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(webhookSecret));
    var hash = hmac.ComputeHash(Encoding.UTF8.GetBytes(payload));
    var expected = Convert.ToHexString(hash).ToLowerInvariant();
    return CryptographicOperations.FixedTimeEquals(
        Encoding.UTF8.GetBytes(expected),
        Encoding.UTF8.GetBytes(receivedSignature)
    );
}
go
import (
    "crypto/hmac"
    "crypto/sha256"
    "encoding/hex"
    "fmt"
)

func isValidSimastRequest(applicationUUID, demandeDetailUUID, timestamp, receivedSignature, webhookSecret string) bool {
    payload := fmt.Sprintf("%s.%s|%s", timestamp, applicationUUID, demandeDetailUUID)
    mac := hmac.New(sha256.New, []byte(webhookSecret))
    mac.Write([]byte(payload))
    expected := hex.EncodeToString(mac.Sum(nil))
    return hmac.Equal([]byte(expected), []byte(receivedSignature))
}

  • If the signature is invalid or the timestamp is stale, the endpoint should return 401 Unauthorized and not return any data.

Secret rotation: SIMAST always signs the pull URL with whatever webhook_secret is active at the moment of the actual pull — not the one active when the request was created. Same grace-period behavior as the webhook POST signature applies: after regenerating your webhook_secret, the previous one stays valid for 24h, so retry verification with the previous secret if the current one fails during that window. See Secret rotation for details.

Full Lifecycle ​

Step 1 — Third-party creates a data request ​

js
axios.defaults.headers.common['Authorization'] = ACCESS_TOKEN;

axios.post('BASE_URL/v1/third-app/activities/activity:uuid/demandes',
  {
    "name": "PRO_2_ACT_1_REQUEST 1.0",
    "description": "...",
    "quantity": 100,
    "fields": ["department", "commune", "section", "nom_chef", "prenom_chef"],
    "filters": [
      [
        ["departement", "in", ["8"]],
        ["commune", "in", ["814"]]
      ]
    ]
  },
  { headers: { 'Content-Type': 'application/json' } }
)

The exact signature, X-Webhook-Timestamp, and X-Webhook-Signature aren't fixed at this point — they're computed by SIMAST at the moment of the actual pull (Step 4 below), using the Application's webhook_secret active at that time, not the one active when the request was created. Assuming callback_url = https://third-app.example.com/simast/callback, the URL shape is (the trailing /{hmac_signature} segment is the current, compatibility-preserving shape — see the migration path note above, it is not permanent):

https://third-app.example.com/simast/callback/{demandeDetail_uuid}/{hmac_signature}

Step 2 — Third-party retrieves data via the API ​

While waiting for SIMAST's retro pull, the third-party can independently fetch its shared data:

js
axios.get('BASE_URL/v1/third-app/demandes/demande:detail:uuid/data',
  {
    params: { current_page: 1, per_page: 50 },
    headers: { 'Content-Type': 'application/json' }
  }
)

Step 3 — Internal processing by the third-party ​

The third-party application processes the received data internally:

  • Verification of the shared data
  • Updating existing records in its database
  • Distribution of relevant information
  • Any other internal operations required

Notification in between: once the request is approved and data processing is complete (or fails), SIMAST also sends a POST webhook notification (demande.completed/ demande.failed) to callback_url — a separate, independently-signed mechanism. See Webhooks for the full payload and signature verification. Receiving this notification does not mean the retro pull below will follow automatically — the two are unrelated.

Step 4 — SIMAST pulls data from the return URL (independent, on-demand) ​

At a later time — chosen internally by SIMAST/the partner, with no fixed schedule and no automatic trigger from the webhook above — SIMAST performs a GET on the signed URL, signed at this exact moment with the Application's current webhook_secret and built from callback_url, to retrieve updated data from the third-party application:

GET https://third-app.example.com/simast/callback/{demandeDetail_uuid}/{hmac_signature}
X-Webhook-Timestamp: {timestamp}
X-Webhook-Signature: {hmac_signature}

The third-party endpoint must:

  1. Extract demandeDetail_uuid from the path, and the signature from either the last path segment (legacy) or the X-Webhook-Signature header (recommended) — same value either way
  2. Verify the signature using the webhook_secret, and reject if X-Webhook-Timestamp is more than ~5 minutes old
  3. Return the data in the format below

Expected Response Format ​

The return URL endpoint must respond with 200 OK and Content-Type: application/json.

In addition to the standard household/member fields, every household carries:

  • beneficiary (Boolean, required): true if the household has actually received assistance from your program for this activity. Must be a JSON boolean (true / false). Strings such as "true", "OUI" and numbers are not accepted.
  • interventions (Array): the assistance received. Required and non-empty when beneficiary is true; ignored when false. See Interventions.
  • support_nature (String, optional): free-text description of the assistance.

Interventions ​

Each item describes one kind of assistance received by the household:

FieldTypeRequiredDescription
intervention_typeStringtrueIntervention type UUID. Must be one of the intervention types of the activity
modalityStringtrueCASH (cash, mobile money, cash-value voucher), IN_KIND (goods), SERVICE (training, care, support)
amountNumberfalseCASH only. Total amount received over the activity. Must be greater than 0
currencyStringfalseCASH only, required with amount: HTG or USD

amount and currency go together, and are only accepted with CASH. Non-monetary assistance is described by its type and modality only.

Interventions whose type belongs to the Collective actions category (COLLECTIVE, see Intervention types) are accepted but don't make the household count as a beneficiary for other programs.

Invalid households are skipped: a household that doesn't follow these rules is ignored, along with its members. The other households in the response are still processed. SIMAST is the caller here, so no error is sent back to your endpoint: validate the payload on your side.
