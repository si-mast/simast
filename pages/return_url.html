Return URL ​

Concept ​

The return_url is a field provided when creating a data request (POST /activities/{uuid}/demandes). It is the base URL of an endpoint hosted by the third-party application that SIMAST will call to retrieve updated data after the request has been processed.

SIMAST constructs the actual call URL by appending the DemandeDetail UUID and an HMAC-SHA256 signature to the base URL:

GET {return_url}/{demandeDetail_uuid}/{hmac_signature}

This means the third-party application must expose a GET endpoint that accepts two path segments after the base path.

Security — Signature Verification ​

The URL called by SIMAST is signed using HMAC-SHA256 with the webhook_secret configured on the application (set during application registration via the Partner portal).

The third-party application must verify this signature before returning any data. This ensures that only SIMAST can trigger the retro pull.

The signed payload is the application UUID and the DemandeDetail UUID joined by |, not the DemandeDetail UUID alone.

Verification logic (example in Node.js):

js
const crypto = require('crypto');

function isValidSimastRequest(applicationUuid, demandeDetailUuid, receivedSignature, webhookSecret) {
  const expected = crypto
    .createHmac('sha256', webhookSecret)
    .update(`${applicationUuid}|${demandeDetailUuid}`)
    .digest('hex');
  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(receivedSignature)
  );
}

If the signature is invalid, the endpoint should return 401 Unauthorized and not return any data.

Full Lifecycle ​

Step 1 — Third-party creates a data request ​

js
axios.defaults.headers.common['Authorization'] = ACCESS_TOKEN;

axios.post('BASE_URL/v1/third-app/activities/activity:uuid/demandes',
  {
    "name": "PRO_2_ACT_1_REQUEST 1.0",
    "description": "...",
    "quantity": 100,
    "fields": ["department", "commune", "section", "nom_chef", "prenom_chef"],
    "filters": [
      [
        ["departement", "in", ["8"]],
        ["commune", "in", ["814"]]
      ]
    ],
    "return_url": "https://third-app.example.com/simast/retro"
  },
  { headers: { 'Content-Type': 'application/json' } }
)

SIMAST stores the return URL and internally constructs the signed URL:

https://third-app.example.com/simast/retro/{demandeDetail_uuid}/{hmac_signature}

Step 2 — Third-party retrieves data via the API ​

While waiting for SIMAST's retro pull, the third-party can independently fetch its shared data:

js
axios.get('BASE_URL/v1/third-app/demandes/demande:detail:uuid/data',
  {
    params: { current_page: 1, per_page: 50 },
    headers: { 'Content-Type': 'application/json' }
  }
)
JSON
{
  "data": [
    {
      "id": 0,
      "code": "string",
      "version": 0,
      "departement": 0,
      "commune": 0,
      "...[Household fields included in the request]",
      "membres": [
        "...[Member fields included in the request]"
      ]
    }
  ],
  "meta": {
    "current_page": 1,
    "from": 1,
    "per_page": 50,
    "to": 50,
    "total": 100,
    "last_page": 2
  }
}

Step 3 — Internal processing by the third-party ​

The third-party application processes the received data internally:

  • Verification of the shared data
  • Updating existing records in its database
  • Distribution of relevant information
  • Any other internal operations required

Step 4 — SIMAST sends a webhook notification ​

Once the request is approved and data processing is complete, SIMAST notifies the third-party application by sending a POST request to the callback_url configured on the application:

POST {callback_url}
X-Webhook-Signature: {signature}
X-Webhook-Event: demande.completed
X-Webhook-ID: {uuid}

{
  "event": "demande.completed",
  "company_id": "uuid",
  "application_id": "uuid",
  "data": {
    "demande_uuid": "uuid",
    "name": "string"
  },
  "timestamp": "2026-04-10T12:00:00Z"
}

Note: This webhook only signals that the initial data request has completed. It is not linked to the retro pull described below — the two mechanisms are independent, and receiving this webhook does not mean a retro pull will follow automatically.

If the extraction fails instead (e.g. an internal SIMAST error while fetching household data), SIMAST sends the same kind of notification with a different event:

POST {callback_url}
X-Webhook-Signature: {signature}
X-Webhook-Event: demande.failed
X-Webhook-ID: {uuid}

{
  "event": "demande.failed",
  "company_id": "uuid",
  "application_id": "uuid",
  "data": {
    "demande_uuid": "uuid",
    "name": "string",
    "demande_detail_uuid": "uuid"
  },
  "timestamp": "2026-04-10T12:00:00Z"
}

The corresponding DemandeDetail also carries status: "FAILED", plus last_error (the error message) and failed_at (timestamp), retrievable at any time via the request detail endpoint — useful if the webhook delivery itself is missed.

Step 5 — SIMAST pulls data from the return URL (independent, on-demand) ​

At a later time — chosen internally by SIMAST/the partner, with no fixed schedule and no automatic trigger from the webhook above — SIMAST performs a GET on the signed return URL to retrieve updated data from the third-party application:

GET https://third-app.example.com/simast/retro/{demandeDetail_uuid}/{hmac_signature}

The third-party endpoint must:

  1. Extract demandeDetail_uuid and hmac_signature from the path
  2. Verify the signature using the webhook_secret
  3. Return the data in the format below

Expected Response Format ​

The return URL endpoint must respond with 200 OK and Content-Type: application/json.

In addition to the standard household/member fields, two fields are required:

  • beneficiary (Boolean): whether the individual is a beneficiary of the third-party program
  • support_nature (String | null): the nature of support provided; null if not applicable
json
{
  "data": [
    {
      "id": 0,
      "code": "string",
      "version": 0,
      "departement": 0,
      "commune": 0,
      "...[Household fields included in the shared request]",
      "beneficiary": true,
      "support_nature": "text | null",
      "membres": [
        "...[Member fields included in the shared request]"
      ]
    }
  ],
  "meta": {
    "current_page": 1,
    "from": 1,
    "per_page": 50,
    "to": 50,
    "total": 100,
    "last_page": 2
  }
}

Note: Retro data returned through this mechanism is stored separately by SIMAST and goes through a data quality review before being merged into the main household/member tables.
